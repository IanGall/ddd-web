# ADR 0002: 生成物目录策略与例外治理

## 状态

已采纳（日期：2026-09-16）

## 背景

shadcn/ui 采用 Vendored Code（代码所有权）模式，基础组件代码直接由 CLI 生成至工程目录（`src/components/ui/` 与 `src/hooks/use-mobile.ts`）。
该模式赋予了应用对组件源码的完全掌控权，但也带来了两类工程挑战：

1. 若业务代码随意侵入修改生成物，会导致代码所有权界限模糊、上游更新覆盖（`shadcn add <name> --overwrite`）困难，且多人在不同提交中散落修改，难以溯源；
2. 自动化代码格式化（Prettier）若处理生成物目录，一方面会在初始 35 个生成物上产生巨大的非功能性 diff，另一方面每次执行 `shadcn add` 引入新组件时都会因格式微调立刻破坏 `pnpm format` 门禁。

## 决策

1. **生成物「不手改」口径与分层架构**：
   - 规定 `src/components/ui/` 下的代码为无样式基座生成物，严禁直接在其内部填充业务逻辑或修改默认样式行为。
   - 所有交互扩展、数据绑定或样式覆盖，一律在 `src/components/<Name>/` 目录下建立上层封装组件。
   - 现有规范落地范例：
     - `LoadingButton`：封装 `Button`，增加 loading 状态与 spinner；
     - `ClearableSelect`：封装 `Select`，增加一键清空与 `alignItemWithTrigger={false}` 展开定位；
     - `ConfirmPopover`：封装 `Popover`，增加轻量级二次确认交互与异步 loading；
     - `TagInput`：基于 `Input` 与 `Badge` 组合实现键盘可控的标签输入；
     - `StatusBadge`：基于 `Badge` 提供 12 种语义色状态变体；
     - `Tree`：基于 `Checkbox` 构建满足 WAI-ARIA 标准的受控权限树；
     - `DataTable`：基于 `Table` 与 `Pagination` 结合 TanStack Table v9 实现服务端表格；
     - `ThemeToggle`：基于 `DropdownMenu` 实现浅色/深色/系统跟随切换。

2. **生成物目录加入 `.prettierignore`**：
   - 将 `src/components/ui` 显式写入 `.prettierignore`。
   - 理由：全量格式化会在 35 个生成物文件上产生一次性大 diff，且每次执行 `shadcn add` 引入新组件时都会重新让 `pnpm format` 变红。忽略该目录后，新增组件永远不会破坏 CI 门禁，也使得本仓文件与上游注册表模板之间的 `diff` 具备确定且有意义的对照价值。
   - 严格划界：`src/index.css` 属于本项目自主编写的核心样式源，必须照常参与 Prettier 格式化，严禁忽略。

3. **两处已存在的例外及其自动化门禁守卫**：
   全仓当前存在且仅存在两处对 shadcn 上游模板的改动，各自拥有严格的自动化门禁守卫：
   - **例外 1：`src/components/ui/scroll-area.tsx`**：删掉了一行未被使用的 `import * as React`。
     - 守卫门禁：`tsconfig.json` 开启了 `"noUnusedLocals": true`。若未来该文件被 `shadcn add --overwrite` 意外覆盖并重新带入未使用的 import，`pnpm typecheck` 与 `pnpm build` 会直接报 **TS6133**（`'React' is declared but its value is never read`）错误中断构建。
   - **例外 2：`src/hooks/use-mobile.ts`**：将 upstream 原有的 `useEffect + useState` 监听实现改写为 `React.useSyncExternalStore`。
     - 守卫门禁 A：ESLint 配置了 `react-hooks/set-state-in-effect: error`。若被回退为在 effect 中 setState，`pnpm lint` 立即报错。
     - 守卫门禁 B：`scripts/check-style.sh` 第 7 条红线设立了更早、更明确的专用守卫，使用 `grep -F` 精确匹配真实代码调用行：`return React.useSyncExternalStore(subscribe, getSnapshot, getServerSnapshot);`。此规则刻意不只匹配标识符 `useSyncExternalStore`，因为文件第 3 行的注释中就包含该标识符；若只匹配标识符，将出现「注释留存、代码回退」却被静默放过的严重漏检。
   - **回退代价分析**：这两处例外在被回退时**均会触发门禁变红，绝不会静默漏过**。真实代价仅在于编译器或 linter 的报错信息（TS6133 或 set-state-in-effect）属于通用规则报错，并不直接指明「某某文件被覆盖回退」，排查者需查阅本文档或 check-style 提示即可快速定位。

4. **关键关联依赖保护**：
   `shadcn add` 会自动向 `package.json` 追加 `cmdk`（`src/components/ui/command.tsx` 依赖）与 `next-themes`（`src/components/ui/sonner.tsx` 与全站主题切换依赖），这些属于生成物运行所需的必要依赖，绝不能在依赖清理时手工删除。

## 理由

- **维护边界清晰**：生成物与业务自建组件各司其职，保证了架构的可维护性。
- **CI 门禁稳定**：消除 Prettier 对外部代码模板的摩擦，杜绝新增组件时的格式偶发中断。
- **改动可知可控**：将必要的补丁（TS 干净度与 React 19 最佳实践）纳入可验证的门禁体系。

## 后果（含代价与已知偏离）

- **代价 1：覆盖更新需重新应用补丁**：未来若执行 `shadcn add scroll-area --overwrite` 或 `shadcn add sidebar --overwrite`，需人工复核并重新应用上述两处微调。
- **代价 2：错误报错信息需要常识映射**：当团队成员误操作覆盖文件时，需理解 TS6133 与 set-state-in-effect 背后的真实原因是生成物被上游模板回退。
- **已知偏离**：全仓对上游生成物的偏离严格收敛于上述两处（`scroll-area.tsx` 删未使用 import、`use-mobile.ts` 使用 `useSyncExternalStore`），不存在任何第 3 处未经记录的手改。
